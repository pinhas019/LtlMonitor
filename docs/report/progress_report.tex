\section{The claim}

A robot skill executing in an unstructured environment can deviate from its intended
behaviour; the question is how to tell, early enough to intervene. The claim of this work
is that skill execution can be represented as a finite set of \emph{progress states}: the
\emph{semantic} state of the robot with respect to the task, as equivalence classes of
world--robot configurations indistinguishable with respect to task advancement. Transitions
between them are boolean guards, which is what makes assessment cheap: the semantics live
in the states, the per-tick work is a boolean evaluation.

Two properties follow. \emph{Dimensionality reduction}: the robot's high-dimensional
continuous state --- joint angles, velocities, perception, middleware --- projects onto a
small discrete set of semantically meaningful phases.
\emph{Explainability}: the monitor produces a human-readable trace, so it can say
\emph{why} a failure is imminent rather than only that one is.

The weakness this addresses is the limited context awareness of current language- and
vision-based monitors, which reason only from what is currently observable. Progress
states ground the assessment instead, lifting it out of a single free-text prompt into a
semi-structured state-graph machine --- LangGraph-like --- in which the monitor's position
is explicit and carried between ticks. Because every skill carries the same structure,
task progression is a concatenation of skill progressions and one monitor serves both
levels. Settling the claim needs a measurable gain over the same monitor without progress
states, for learned as well as hand-written skills, and on real hardware.

\section{This repository: two streams}

\url{https://github.com/pinhas019/LtlMonitor} is the ongoing development of the question
this project started from: can a skill described in natural language be lifted to LTL,
given an LTL description of its progress, and monitored against it at runtime? The work
advances in two streams. \emph{Skill description}: a language model drafts the skill's
progress structure, which is converted to LTL and compiled to automata with
Spot~3~\cite{duretlutz2022spot}. \emph{Skill monitoring}: at runtime a language model and
Python boolean guard evaluators supply the atomic propositions, and verdicts follow the
three-valued semantics of Bauer et al.~\cite{bauer2011runtime}, graded from a warning
through to an abort. Named failure modes run as parallel safety monitors, so a fault is
attributed to a named condition rather than to the specification as a whole. One skill's
compiled specification reads, in abbreviated form:

\begin{center}\footnotesize
\begin{tabular}{@{}ll@{}}
progress & \texttt{F(mission\_started \& F(path\_active \& F(moving\_to\_target \& F(mission\_finished))))} \\
safety & \texttt{G(!collision\_risk)}\qquad \texttt{G(upright)} \\
\end{tabular}
\end{center}

\noindent
Each proposition carries an executable rule over the sensor keys the robot's adapter
declares, and a generated description is checked against that schema before it runs, which
is what makes a free-language description executable on the robot it was written for;
existing work instead grounds into a signature fixed in advance, or judges groundedness
with a learned classifier~\cite{english2025ginsign}.

The monitor currently runs against simple tasks in a continuous version of MiniGrid,
integrated with MAAOS, and is under development for monitoring Elias's TRAV navigation
application on the humanoid. MAAOS is Fouzi's project, and I worked on it with him.

\section{Results: where it helped, where it did not, and why}

The ablation runs three arms per scenario --- monitor off, detection-only, detection with
re-planning --- over single-agent and cooperative box-push, at ten seeds per cell for the
deterministic monitors and five for the LLM-backed ones.

\textbf{Where it helped: only when detection was coupled to recovery.} On the corrupted
single-agent plan the unmonitored baseline succeeded in no seed and detection with
re-planning in every one ($\Delta = +1.00$). The cooperative deadlock repeats it:
unmonitored, the run exhausted its 80-step budget and failed in every seed; the rule-based
LTL monitor with re-planning recovered every seed ($\Delta = +1.00$) in about 45 steps, and
the LLM-labelled variant matched it.

\textbf{Where it did not: detection alone, everywhere.} Every detection-only arm scored
$\Delta = +0.00$. Halting at the violation --- step 10 of 80 on the deadlock --- stops the
trajectory drifting further, but stopping is not reaching the goal. The monitor's measured
value is in what the verdict lets the planner do next, not in the verdict.

\textbf{Where it did not: the unstructured LLM judge.} A pure natural-language judge scored
$\Delta = +0.00$ even with recovery enabled, where the LTL monitors scored $+1.00$ on the
same scenario and seeds. A free-text verdict says something is wrong without locating it in
the skill's progress, so the re-planner has nothing specific to act on --- the argument for
progress states, measured.

\textbf{False alarms, and a specification fault.} Clean and hazard-navigation scenarios held
at 1.00 success with zero false alarms across all monitors and arms. The one failure was a
specification fault of my own: a predicate demanded the two agents stay continuously
aligned, whereas the real push skill interleaves alignment with pushing, so the monitor
flagged correct behaviour on every clean run. Relaxing the formula fixed it; a stronger
judge model did not. The fault lay in the description, not the monitor. These runs drove
scripted reference plans rather than the live MAAOS planner, and the figures come from
discrete-mode episodes --- so they establish detection and the value of intervening on it,
but not yet under the planner or in continuous physics.

\section{The G1}

The system was deployed across two tiers --- clock, evaluator and recorder on the robot,
monitor and operator console on the development machine --- and run, recording the episode
as it went; the recording replayed to identical verdicts, so a verdict does not depend on
the machine producing it. It remains under development: only part of the specification was
exercised, the navigation experiment has not run, and good assessment on hardware will need
a vision--language model in the proposition layer, which is not built. The mechanism itself
is embodiment-independent --- the real G1, MuJoCo and Isaac Lab adapters expose an identical
sensor schema over entirely different topics, and one engine runs across all three
unchanged --- and the failure classes caught here are the ones that dominate a humanoid in
an unstructured environment, not gridworld artefacts.

\section{Next steps}

Deploy on the high-fidelity simulator, Isaac Sim or MuJoCo, which is what lets the claim be
evaluated in volume rather than demonstrated, and extend to more skills --- pick-and-place
next, alongside the navigation application and a learned policy. For the proposition layer
the intended direction is a vision--language monitor, with the 2025 MIT work on
vision--language failure detection as the baseline; evaluation follows in two stages, an
ALFWorld ablation comparing the monitor with and without the progress-state description,
then VLABench and NaVila. The literature review on description and monitoring is complete
and the work will be refined against it, including positioning against runtime-verification
tools for ROS~\cite{ferrando2020rosmonitoring,rtamt2024}, which monitor hand-written
specifications rather than ones derived from a skill description.
