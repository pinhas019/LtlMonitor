\noindent
A free-language description of a robot skill is compiled into a runtime monitor
---progress phases, temporal-logic guards and named failure modes--- which then watches
the skill execute and reports where it is and where it is going wrong. The engine is
meant to be skill-agnostic: changing the skill, or the robot, should change the
generated specification and not the engine. The implementation is at
\url{https://github.com/pinhas019/LtlMonitor}.

\section{Approach}

The design separates two concerns. An \emph{adapter} per embodiment describes what a
given robot can sense; a \emph{specification} per skill describes what the skill must
do. Progress is tracked by a phase machine over temporal-logic milestones, while named
failure modes run as parallel safety monitors, so a fault can be attributed to a
condition with a name rather than to the specification as a whole. Automata are built
with Spot~3~\cite{duretlutz2022spot}, and verdicts follow the three-valued
runtime-verification semantics of Bauer et al.~\cite{bauer2011runtime}. Responses are
graded rather than binary, ranging from a warning through to an abort.

A compiled specification for the navigation skill reads, in abbreviated form:

\begin{center}\footnotesize
\begin{tabular}{@{}ll@{}}
progress & \texttt{F(mission\_started \& F(path\_active \& F(moving\_to\_target \& F(mission\_finished))))} \\
safety & \texttt{G(!collision\_risk)}\qquad \texttt{G(upright)} \\
\end{tabular}
\end{center}

\noindent
Each proposition carries an executable rule over the adapter's declared sensor keys, and
a validation oracle checks a generated specification against that schema before it
reaches the engine --- which is what keeps a generated specification runnable on the
robot that will run it. Against the nearest prior work~\cite{english2025ginsign},
grounding here targets a live adapter schema rather than one fixed in advance.

\section{Progress this period}

\textbf{MiniGrid and MAAOS.} The continuous-physics layer over MiniGrid --- float poses,
continuous velocity commands and a micro-step integration of each action --- carries the
multi-agent cooperative box-pushing environment that the monitor is integrated with under
MAAOS. Hazards are extensible by subclassing: a new hazard type brings its own physics,
its monitoring category and the containment flags the monitor consumes, without the
monitor changing.

\textbf{The robot.} The system was deployed across two tiers --- clock, evaluator and
recorder on the Unitree G1, monitor and operator console on the development machine ---
and run on the robot. The recorded episode replayed on the development machine to
identical verdicts throughout, which is the test for the claim that the monitor does not
depend on the machine it runs on. That is the first result on hardware, and a limited
one: the run exercised only part of the specification.

\textbf{Navigation application.} I am working with Elias on the navigation application
intended for deployment on the G1.

\textbf{High-fidelity simulation.} Under development. Three embodiment adapters --- the
real G1, MuJoCo and Isaac Lab --- expose an identical sensor schema over entirely
different topics, so one monitor and one specification run across all three unchanged,
and sensor bridging for Isaac is in place. The purpose is to re-execute episodes as
counterfactuals rather than to visualise them, so the work is gated on fidelity
validation against recorded runs. What remains is to run the robot's own navigation
stack inside the simulator, and scenario reset.

\textbf{Literature.} Ongoing. Twenty papers have been read closely and summarised so
far. The review has settled how this work is positioned against the nearest prior art
and produced a ranked list of corrections to our own implementation, chiefly in how
satisfaction is reported for safety properties.

\section{Assessment}

The engine, the synthesis pipeline and the deployment path are in place and exercised.
Where the monitor has so far shown itself useful is in the MAAOS integration.

Once the navigation application is deployed on the G1, the monitor will be used to
assess it. That will be the first time the monitor is applied to a skill developed
independently of it, which is the sharpest available test of the skill-agnostic claim:
the specification should change and the engine should not.

\section{Next steps}

The pace is set by two things becoming available rather than by a calendar. The first is
the high-fidelity simulation: once it is ready, episodes can be driven automatically and
in volume, which is what the monitor needs in order to be evaluated rather than merely
demonstrated. The second is a wider set of skills --- the claim is that the engine is
skill-agnostic, and testing that needs skills beyond navigation, which is where the
navigation application and further MAAOS skills come in.

Alongside those, we intend to compare this monitor against existing runtime-verification
tools for ROS~\cite{ferrando2020rosmonitoring,rtamt2024}, on the axes where we expect to
differ: synthesis of the specification from a free-language description, grounding in a
declared sensor schema, and portability of one specification across embodiments.
