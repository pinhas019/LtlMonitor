\noindent
A free-language description of a robot skill is compiled into a runtime monitor
---progress phases, temporal-logic guards and named failure modes--- which then watches
the skill execute and reports where it is and where it is going wrong. The engine is
meant to be skill-agnostic: changing the skill, or the robot, should change the
generated specification and not the engine. This report summarises where that work
stands across its three strands and what the coming weeks hold.

\section{Approach}

The design separates two concerns. An \emph{adapter} per embodiment describes what a
given robot can sense; a \emph{specification} per skill describes what the skill must
do. Progress is tracked by a phase machine over temporal-logic milestones, while named
failure modes run as parallel safety monitors, so a fault can be attributed to a
condition with a name rather than to the specification as a whole. Automata are built
with Spot~\TODO{version}~\cite{duretlutz2022spot} and verdicts follow the three-valued
runtime-verification semantics of Bauer et al.~\cite{bauer2011runtime}. Responses are
graded rather than binary, ranging from a warning through to an abort.

What makes the pipeline usable is a validation oracle. A specification generated from a
free-language description is checked mechanically against the adapter's declared sensor
schema before it is allowed near the engine, which is what keeps a generated
specification executable on the robot that will run it. Against the nearest prior
work~\cite{english2025ginsign}, grounding here targets a live adapter schema rather than
one fixed in advance, and the evaluation is on a robot rather than a benchmark.

\section{Progress this period}

\textbf{Continuous-world MiniGrid.} The continuous-physics layer over MiniGrid --- float
poses, continuous velocity commands, and a micro-step integration of each action ---
now carries the multi-agent cooperative box-pushing environment that the monitor stack
sits on. Hazards are extensible by subclassing: a new hazard type brings its own
physics, its monitoring category and the containment flags the monitor consumes, without
the monitor changing. Two physics backends, a Python reference and a compiled core, are
held to each other by parity tests. The suite is green apart from one open
numerical-tolerance issue.

\textbf{The robot.} The system was deployed across two tiers --- clock, evaluator and
recorder on the Unitree G1, monitor and operator console on the development machine ---
and run on the robot. The recorded episode replayed on the development machine to
identical verdicts throughout, which is the acceptance test for the claim that the
monitor does not depend on the machine it runs on. That is the first result on real
hardware, and a limited one: the run exercised only part of the specification, and the
full navigation experiment has not yet taken place.

\textbf{High-fidelity simulation.} Three embodiment adapters --- the real G1, MuJoCo and
Isaac Lab --- expose an identical sensor schema over entirely different topics, so one
monitor and one specification run across all three unchanged. Sensor bridging for Isaac
is settled. The purpose here is to re-execute episodes as counterfactuals rather than to
visualise them, so the work is gated on fidelity validation against recorded runs. What
remains is to run the robot's own navigation stack inside the simulator rather than a
stand-in, and to implement scenario reset so that episodes can be driven automatically.

\textbf{Literature and positioning.} Twenty papers were read closely and summarised. The
review settled how this work is positioned against the nearest prior art and, in the
process, produced a ranked list of corrections to our own implementation --- chiefly in
how satisfaction is reported for safety properties --- which are now scheduled rather
than open-ended.

\section{Assessment}

The engine, the synthesis pipeline and the deployment path are in place and exercised,
and the test suite --- 1242 cases, ROS-free by construction --- runs on every change.
What is not yet in place is evidence. The monitor has been shown to be portable and
deterministic; it has not yet been shown to be \emph{useful}, because the navigation
experiment that would measure detection and recovery has not run. Integration of the
TRAV navigation stack on the G1 is close to complete, and that experiment is the
immediate priority. Everything downstream --- the simulation work and the comparison
between detection alone and detection with recovery --- depends on the recording it
produces, which is why the schedule below is sequential rather than parallel.

\section{Risks to the schedule}

Two things could move these dates. The navigation experiment depends on TRAV integration
completing on the robot, and throughout this project hardware availability, rather than
software readiness, has been the binding constraint. Separately, the simulation strand is
worth exactly what its fidelity validation says it is worth: if too many recorded
episodes fall outside tolerance, counterfactual re-execution stops being usable as
evidence and the comparison has to move back onto the robot, which is considerably
slower. Both risks surface early --- the first on 11 September, the second on 9 October
--- rather than at the end.
