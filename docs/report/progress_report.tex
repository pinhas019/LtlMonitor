\section{The claim}

A robot skill executing in an unstructured environment deviates from its intended
behaviour; the question is how to tell, early enough to intervene. The claim of this work
is that skill execution can be represented as a finite set of \emph{progress states}:
equivalence classes of world--robot configurations that are indistinguishable with respect
to task advancement, connected by boolean transition guards. A monitor that tracks which
progress state a skill is in, rather than judging success from the current observation
alone, is both cheaper to evaluate and harder to mislead.

Two properties follow. \emph{Dimensionality reduction}: the robot's high-dimensional
continuous state --- joint angles, velocities, perception, process and middleware state
--- projects onto a small discrete set of semantically meaningful phases.
\emph{Explainability}: the monitor produces a human-readable trace, so it can say
\emph{why} a failure is imminent rather than only that one is.

The weakness this addresses is the limited context awareness of current language- and
vision-based monitors, which reason from what is currently observable. If a robot drops
an object at the placement location, such a monitor sees no object in frame, sees that it
is at the placement location, and concludes the skill succeeded. A progress-state monitor
knows the skill never left \texttt{goTo placement location}, and reports failure. Because
every skill carries the same structure, task progression is a concatenation of skill
progressions and one monitor serves both levels.

Three things would settle the claim: that progress-state descriptions can be produced for
both coded and learned skills; that a monitor given them measurably outperforms the same
monitor without them; and that this holds on a real humanoid, not only in benchmark
environments.

\section{How it works}

The progress states of a skill appear in the implementation as \emph{phases}, and their
transition guards as temporal-logic formulae; named failure modes run as parallel safety
monitors, so a fault can be attributed to a condition with a name rather than to the
specification as a whole. Guards are compiled to automata with
Spot~3~\cite{duretlutz2022spot} and verdicts follow the three-valued semantics of Bauer
et al.~\cite{bauer2011runtime}. Responses are graded, from a warning through to an
abort. A compiled specification for the navigation skill reads, in
abbreviated form:

\begin{center}\footnotesize
\begin{tabular}{@{}ll@{}}
progress & \texttt{F(mission\_started \& F(path\_active \& F(moving\_to\_target \& F(mission\_finished))))} \\
safety & \texttt{G(!collision\_risk)}\qquad \texttt{G(upright)} \\
\end{tabular}
\end{center}

\noindent
Each proposition carries an executable rule over the sensor keys the robot's adapter
declares. A generated description is checked against that schema before it is allowed to
run, which is what makes a description written in free language executable on the robot it
was written for; existing work instead grounds into a signature fixed in advance, or
judges groundedness with a learned classifier~\cite{english2025ginsign}. The
implementation is at \url{https://github.com/pinhas019/LtlMonitor}.

\section{Progress this period}

\textbf{MiniGrid and MAAOS.} The continuous-physics layer over MiniGrid carries the
multi-agent cooperative box-push environment the monitor runs against. Three
specifications are loaded: one task-level, and one for each MAAOS skill. It watches a
coordination sequence (reach the box, align, push together, place it on target), safety
guards around lava and loss of the push formation, and a deadlock condition on both
agents' poses. Adding a skill is a specification file and nothing else;
adding a hazard type still requires a change in the environment as well.

\textbf{The robot.} The system was deployed across two tiers --- clock, evaluator and
recorder on the Unitree G1, monitor and operator console on the development machine ---
and run on the robot, recording the episode as it went. It is the first result on
hardware, and a limited one: the run exercised only part of the specification.

\textbf{Navigation application.} I am working with Elias on the navigation application
intended for deployment on the G1.

\textbf{High-fidelity simulation.} Under development; sensor bridging for Isaac is in
place. Its purpose is to re-execute episodes as counterfactuals rather than visualise
them, so it is gated on fidelity validation against recorded runs. What remains is the
robot's own stack inside the simulator, and scenario reset.

\textbf{Literature.} Ongoing. Twenty papers read closely and summarised so far; the
review has settled how the work is positioned against the nearest prior art, and produced
a ranked list of corrections to our own implementation.

\section{How far the claim has got}

\textbf{First condition.} Progress-state descriptions exist for navigation and for the
MAAOS skills --- three specifications are loaded, one task-level and one per skill --- and
adding a skill is a specification file alone, with one engine running unchanged across
three embodiments. All are coded skills; nothing has yet been described for a learned
policy, the harder half of the condition.

\textbf{Second condition.} The cooperative box-push work gives the first direct
comparison. On an injected-deadlock scenario the unmonitored run exhausted its whole
80-step budget and failed in every seed; detection alone halted it at step 10, and halt
plus a single re-plan turned the same scenario into a success in every seed, in 45 steps,
with no false alarms on clean or non-fatal-hazard runs. A second case
cuts the other way: against the real push skill, two predicates demanded a formation it
never sustains, so the monitor was flagging correct behaviour and the fault lay in the
description. These runs drove scripted reference plans rather
than the live MAAOS planner, so they establish detection and the value of intervention,
but not yet either under the planner.

\textbf{Third condition.} The G1 recording replayed to identical verdicts, so the monitor
does not depend on the machine it runs on; the navigation experiment itself has not run. Once the navigation application is
deployed, the monitor will be used to assess it --- the first skill developed
independently of the monitor.

\section{Next steps}

The pace is set by two things becoming available rather than by a calendar. The first is
the high-fidelity simulation: once it is ready, episodes can be driven automatically and
in volume, which is what the claim needs to be evaluated rather than demonstrated. The second is a wider set of skills --- the navigation application,
further MAAOS skills, and a learned policy, which is what the first condition needs.

The monitor is currently evaluated by a language model. The intended direction is a
vision--language monitor, taking the 2025 MIT work on vision--language failure detection
as the baseline to build on; none of that is built yet. Evaluation follows the same two
stages: an ablation on ALFWorld comparing the same monitor with and without the
progress-state description, and then VLABench and NaVila once the vision--language monitor
exists. Alongside those, we intend to position the work against existing
runtime-verification tools for ROS~\cite{ferrando2020rosmonitoring,rtamt2024}, which
monitor hand-written specifications rather than ones derived from a skill description.
